# Journal — 2026-10-07 — Session 01: fault F2

## What happened
- **Decided what F2 means.** When the gateway answers 429, the payment fails. It is not treated as an unavailable gateway. This follows the vision's symptom, "burst of failed payments" (`docs/vision.md:32`).
- **fault-f2** ([feature](../../odd/tasks/fault-f2.md)):
  - gateway-mock has an `errorStatus` behavior that accepts 429, 500 or 503.
  - payment-service has a `FAILED` status, a Flyway V2 migration that leaves V1 untouched, the 429 → `FAILED` mapping with a WARN line, and a `lab_payments{status}` gauge.
  - order-service maps `FAILED` to `PAYMENT_FAILED`.
  - The dashboard is now "Lab — Faults" and has two F2 panels.
  - The verify scripts share `lib.sh`, and there is a new `verify-f2.sh`.
- **Real runs.** `verify-f2.sh` passed: 3 orders ended `PAYMENT_FAILED`, both counters rose by 3, the Loki WARN line appeared with the panel's phrase, and an order was `PAID` again after the reset. `verify-f1.sh` still passes on the same stack.
- **Reviews.** Every range was reviewed and approved. The T4 WARNINGs were fixed: the Loki check now proves the panel's filter matches, and the baseline wait is linked to the scrape interval.

## Decisions and why
- **429 → `FAILED`, not 503.** F1 and F2 must leave different traces, otherwise the agent cannot tell them apart. It also matches the vision.
- **`FAILED` is a separate status from `DECLINED`.** A card decline and a gateway rate limit are different causes, and the fault injector's ground truth needs that distinction. Both still end the order in `PAYMENT_FAILED`.
- **A V2 migration, not an edit to V1.** Compose volumes may already have applied V1.
- **The "Gateway rejections" panel counts Loki log lines.** payment-service's `RestClient` exports no client metrics, and a `FAILED` counter would repeat the panel next to it. The log line names the cause and is an independent source.
- **Stable baselines in the verify scripts.** A healthy order is briefly `PAYMENT_PENDING`, so a single scrape could catch it. This happened in a real run. Baselines now need two reads that agree, one scrape interval apart.
- **Standing preferences applied:** feature-branch-chain without asking, and review consent always granted.
- **Process lesson:** the review script used `rg`, which that shell does not have, so the acknowledgement output was lost. The burn was confirmed with `assess` (`already_reviewed`), and the script now uses `grep`.
