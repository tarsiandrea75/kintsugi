# Journal — 2026-10-07 — Session 03: fault F4 and inventory-service (autonomous)

This session continued the autonomous run the user authorized. The quota ran out once mid-feature and work resumed after the reset.

## What happened
- **inventory-service** ([feature](../../odd/tasks/fault-f4.md)):
  - an Initializr skeleton;
  - the stock schema, seeded with SKU-1…SKU-5 at 1,000,000 units each;
  - atomic reservations; lines are merged by SKU and locked in SKU order after a real deadlock showed up in a test;
  - a lab-only reservation-delay hook;
  - explicit Hikari settings, and a 500 with a single WARN line on pool exhaustion.
- **order-service:**
  - `ServiceRestClients` now holds the shared, instrumented RestClient setup;
  - a new `InventoryClient`;
  - orders are reserved before they are saved: 409 when stock is short, 503 when inventory is unavailable, nothing stored in either case;
  - the reservation outcome switch is now compiler-checked.
- **Lab:**
  - inventory-service and its database are in compose, and F4 is injected with `INVENTORY_POOL_SIZE` and `INVENTORY_RESERVATION_DELAY`;
  - a Prometheus target, plus the panels "inventory DB pool" and "inventory 5xx rate";
  - `verify-f4.sh`.
- **Real runs:** `verify-f4.sh` passed (6 of 6 orders 503, Hikari pending 4, timeouts 4). `verify-f1.sh`, `verify-f2.sh` and `verify-f3.sh` still pass on the same stack.
- **M1 check met.** F1–F4 are visible in Grafana.

## Decisions and why
- **Reserve before saving the order.** Stock exists before an order is accepted, and an inventory failure shows up as an error on order. That prepares F8, "timeouts appear on order, root cause is inventory". To review.
- **Inject F4 through compose variables and a recreate.** This is the same mechanism as F3, and it is realistic: a bad config arrives with a redeploy. To review.
- **Hikari exhaustion surfaces as `CannotCreateTransactionException`.** Spring already returns 500 for it, but logs an ERROR stack trace. A handler scoped to the controller keeps the 500 and logs one readable WARN line, which is clearer evidence for the agent.
- **Lock reservation lines in SKU order.** A test reproduced a real PostgreSQL deadlock between two reservations that listed their SKUs in opposite orders.
- **The interrupted review was redone as a new START.** A docs commit made after the quota stop had moved HEAD, so no manual recovery was attempted.
