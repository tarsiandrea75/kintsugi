# Journal — 2026-10-07 — Session 02: fault F3 (autonomous)

The user went to sleep and authorized autonomous work until the current usage quota ran out. Design decisions taken without the user are marked "to review" in the feature document.

## What happened
- **fault-f3** ([feature](../../odd/tasks/fault-f3.md)):
  - order-service's payment client now records `http.client.requests`, tagged by the real I/O failure.
  - Compose takes an `ORDER_PAYMENT_BASEURL` override, which is the F3 injection.
  - New `verify-f3.sh` script and a dashboard panel for order → payment call outcomes.
- **Real runs.** `verify-f3.sh` passed, and the order under F3 answered in about 0.3 s. `verify-f1.sh` and `verify-f2.sh` still pass on the same stack.
- **Review fixes to the verify scripts.** They report transport failures as FAIL instead of aborting, and the in-flight window can no longer include the healthy order.

## Decisions and why
- **Break order-service's payment URL, not payment-service's gateway URL.** This keeps the evidence (the WARN line and the client metrics) in the service where the symptom shows. To review.
- **Tag the inner I/O exception.** Spring Framework 7 tags every I/O failure `ResourceAccessException`, which would make F1 and F3 identical in metrics. A small observation convention tags `ConnectException` (F3) and `HttpTimeoutException` (F1) instead.
- **The evidence is `ConnectException` plus the wrong URL, not "Connection refused".** The JDK's `ConnectException` has a null message, so that text never appears in the logs. The WARN line now names the exception and the URL. Whether to reword `docs/vision.md:33` is to review.
- **Read the baseline after the recreate.** Recreating a container resets its counters.
