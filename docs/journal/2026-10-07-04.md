# Journal — 2026-10-07 — Session 04: living docs, F4 approval and event recording

## What happened
- **Morning review of the autonomous work.** The human accepted the F3 evidence (`ConnectException`) and asked that everything stay reproducible and traceable to living documentation, the single source of truth. `docs/vision.md:33` and the lab-observability spec were aligned with reality.
- **F4 design approved, with a new requirement.** Every attempt and every event must be recorded ("più papisti del papa"). The F4 stock leak was explained step by step: order-service gives up at 3 s, while inventory still reserves at 5 s.
- **event-recording** ([feature](../../odd/tasks/event-recording.md)):
  - Append-only event tables in order-service, inventory-service and payment-service.
  - Rejected orders are kept with terminal statuses.
  - gateway-mock logs a structured line per call.
  - When the database is unreachable, the event is written as a structured WARN line instead.
  - `verify-f4.sh` now proves the leak from data.
- **Reviews.** Every range was reviewed and approved. The review findings that were fixed:
  - a rejection needed a second connection under pool exhaustion; it now uses a savepoint;
  - narrow catches could mask the real outcome;
  - an ambiguous commit was recorded as ERROR; it is now COMMIT_UNKNOWN;
  - a log/doc mismatch;
  - stale STATE entries and a wrong date.

## Decisions and why
- **Living documentation is the single source of truth.** When behavior and a document differ, the document is updated in the same change. Journals are history and are never rewritten.
- **Rejected orders are stored with a terminal status, and every service has an append-only event table.** Evidence the agent cannot read does not exist. The vision's `queryDb` tool will read these tables in M2.
- **When the database is unreachable, the event goes to a structured WARN log line.** It is the only place left. This limit is stated in the specs.
- **A failure to record an event never masks the primary outcome.** When the event shares a transaction with a state change, both fail together.
- **COMMIT_UNKNOWN exists to keep the evidence honest.** A commit can fail after the server actually committed, so recording ERROR there would be false.
